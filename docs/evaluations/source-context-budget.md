# 章节原文预算的离线评估

2026-09-08 完成 M4。生产代码基线为 `b12a8f6`，本轮新增评估入口、历史运行清单和离线回归，没有调整默认预算或报告提交规则。

## 方法与复现

评估入口是 `tests/eval_report_source_context.py`。它调用实际的章节状态机、快照读取和 prompt 组装逻辑，以确定性响应替代模型，以内存记录替代章节提交。正文只在临时目录构造，历史运行只读；调用次数表示工作流调用响应替身的次数，不是实际 API 请求数。成功保存替身章节不表示正文通过真实引用校验或报告质量评测。

固定应用预算为 32,768 tokens，输出预留为 8,192，安全余量为 1,024，因此输入上限为 **23,552 tokens**。原文增量分别测试 1,000、2,000、4,000 tokens。使用 `o200k_base`，模板时间固定为 `2026-09-08 00:00:00`。每次实际传给响应替身的完整 prompt 都重新计数，并与运行时审计比较。

```bash
# 输出目录必须尚不存在，并与历史来源目录分离。
uv run python tests/eval_report_source_context.py \
  --output-dir outputs/source_context_eval_m4_verified

# 没有本地历史产物时，只运行构造案例。
uv run python tests/eval_report_source_context.py \
  --fixtures-only --output-dir outputs/source_context_eval_fixtures

# 验证统计口径、复现性、配置恢复和只读边界。
uv run python tests/test_report_source_context_eval.py
```

已执行的完整结果位于 `outputs/source_context_eval_m4_verified/`，包含 `summary.json`、`summary.md`，以及每个案例、预算下的 `prompts.json` 和章节 `audit.json`。这些是运行产物，不纳入版本控制。汇总记录评估脚本、运行时代码、固定时间后的模板和历史输入文件的 SHA-256。相同输入可在新输出目录重跑；有意再次使用已有目录会失败，避免覆盖记录。

历史目录来自 [`history_runs.json`](../../tests/fixtures/report_source_context/history_runs.json)，缺少目录或输入文件时会标记 `missing_inputs`。构造案例的检查通过不代表缺失的历史样本已经完成统计。本次 6 个目录均可读取，29 章的引用映射没有缺失节点。

## 构造案例结果

8 个构造案例比较三档预算，共 24 组。目标覆盖由 fixture 预先标注的块与目标对应关系计算；它只说明指定块是否进入输入，没有测量模型是否理解材料。长段落有意重复条件说明，以测试完整块超过预算时的行为，不代表真实原文的长度分布。

下表中的斜线表示回读前后，或错误重试中连续调用的顺序。

| 案例 | 1,000 tokens | 2,000 tokens | 4,000 tokens | 正常调用数 |
| --- | --- | --- | --- | ---: |
| 两目标 | 0/2 个目标 | 1/2 个目标 | 2/2 个目标 | 1 |
| 重复 Evidence | 0/2 个目标 | 1/2 个目标 | 2/2 个目标 | 1 |
| 三目标 | 1/3，选中湿度 | 1/3，选中温度 | 3/3 | 1 |
| 表格与标题依赖 | 表格 → 标题、表格 | 表格 → 标题、表格 | 表格 → 标题、表格 | 2 |
| 请求替换自动块 | 无块 → `budget_exceeded` | 温度 → 压力 | 温度、压力 → 压力、温度 | 2 |
| 快照缺失 | `unavailable` | `unavailable` | `unavailable` | 2 |
| JSON 错误、回读、超时、完成 | 回读块超预算 | 原文保留 | 原文保留 | 4，含 2 次失败 |
| 基础输入超限 | `base_prompt_over_budget` | 同左 | 同左 | 0 |

表格案例在所有预算下保留完整表头、35 行数据和脚注；标题通过一次显式结构依赖请求加入。重复案例将温度块关联到多条 Evidence，最终正文块仍只出现一次。

部分实际完整输入如下。原文预算包括引用、读取结果、索引和 JSON 开销，不能直接用它与块正文长度比较。

| 案例 | 原文预算 | 每次完整输入 tokens |
| --- | ---: | --- |
| 三目标 | 1,000 | 6,133 |
| 三目标 | 2,000 | 6,488 |
| 三目标 | 4,000 | 8,445 |
| 请求替换自动块 | 2,000 | 6,357 → 6,203 |
| 表格与标题依赖 | 1,000 | 5,910 → 5,889 |
| 错误重试与回读 | 2,000 | 6,222 → 6,282 → 6,206 → 6,266 |

回读后的输入可以更短，因为程序重新组装视图，并去掉已不需要的可读索引；旧原文没有留在历史消息中。所有实际调用的完整输入和原文增量均未超过各自上限。

## 历史规模下的构造阅读

从 29 章中按候选正文 tokens 排序，选取最小、中位和最大三章，保留完整大纲、目标、候选文字及已有 Evidence—Claim 关系。给前三条 Evidence 构造本地快照，引用编号按 fixture 分配；其余 Evidence 没有快照。回读由脚本指定，不代表真实模型判断。

这一输入没有重建历史 Conflict 视图或原引用注册表，也没有恢复缺失的原文。因此，下表是**历史材料规模下的构造 prompt**，不是历史请求的 token 记录，也不是新功能上线后的输入预测。

| 案例 | 历史章节 | 候选正文 tokens | 构造基础 prompt tokens | 原文预算 2,000 时的输入 |
| --- | --- | ---: | ---: | --- |
| `history-04` | 黄金任务第 4 章 | 1,516 | 10,105 | 11,250 → 10,592 |
| `history-05` | 黄金任务第 5 章 | 6,019 | 19,494 | 21,467 → 19,974 |
| `history-19` | SWF 任务第 1 章 | 15,334 | 35,659 | 基础输入超限，0 次调用 |

最大案例在加入原文前已超过 23,552 tokens 的输入上限，三个原文预算下都进入已有的章节失败路径。增大原文增量不能解决基础材料超限。

两份可调用的历史规模案例在 2,000 与 4,000 档选择相同正文块，并未因预算增大获得更多原文。不同预算还可能只增加可读索引等元数据，所以实际输入增长不能直接解释为覆盖改善。

## 参数结论与验收

保留默认原文预算 **2,000 tokens** 以及已确认的完整应用预算。本次样本验证了预算执行和失败边界，没有建立真实来源分布，也没有证据证明某一档预算改善报告质量。

需保留以下使用边界：

- 完整块可能超过预算，1,000 tokens 甚至可能无法附带任何直接定位块。
- 按目标轮流选块时，小预算跳过的大块在更大预算下可能先被选中，并挤出另一目标的块；本次三目标案例中，覆盖目标集合并不随预算单调扩张。
- 相同块去重不免除 Evidence 关联和索引的输入开销；旧材料没有定位时也不能推断可读的原文。
- 基础材料超限须从完整输入配置或材料组织方式另行讨论，不能由原文预算参数解决。

33 组案例共执行 51 次响应替身调用，包含 6 次脚本注入的失败。所有 token 复核、去重、引用绑定、预期结果和调用边界检查通过。新增评估回归 10 项通过；M3 的 24 项原文回归、Reporter 工作流和回放入口回归也通过。真实自动选择命中率、模型回读率、调用费用和报告质量尚未测量；这些需要另行安排带原文快照的新运行。
